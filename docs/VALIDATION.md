# Validation

Validated locally on 2026-10-30 with Node.js 24.22.1.

- JavaScript syntax checks passed for the Worker, PayPal client, Durable Object, and browser code.
- 154 automated tests passed using Node's built-in test runner, mocked PayPal HTTP responses, simulated persistent Durable Object storage, and a simulated browser DOM/SDK.
- Covered authentication on pages/assets/APIs, cross-origin request rejection, both checkout paths, token scoping, cache persistence and replacement, stale pages, out-of-order callbacks, idempotency/restart recovery, pending captures/vaulting, and verified asynchronous vault events.
- A receiver-sensitive fetch regression test reproduces the original adapter's failure and verifies OAuth, Orders, and scoped-token requests use the Worker global receiver. Error tests distinguish network, timeout, abort, and invocation failures without returning raw exceptions or credentials.
- Controlled-clock tests verify that create/capture calls reuse the REST token for its reported `expires_in` lifetime, renew at expiry, and cache each replacement using its own lifetime without extending it by network time. Concurrent callers share one OAuth exchange. Failed renewals never send an expired token and can be retried; missing/invalid lifetimes are rejected. Vault-scoped SDK tokens remain separate from the REST cache.
- Frontend checks verify that the returning checkout shows the Order ID on creation and the completed capture's Transaction ID after payment, including direct-payment recovery and pending captures. Manual diagnostic responses are logged without changing the displayed receipt.
- Returning-customer approval makes no capture call. Tests verify capture only after Place order, direct payment when there was no edit, repeated edits, cancellation, duplicate clicks, reload/redirect recovery, and lost capture responses. The new-customer flow still captures after approval.
- Trace tests compare displayed requests/responses with the actual PayPal HTTP calls, verify persistence and replay, and cover failed captures and non-JSON errors. Bearer tokens are redacted in immediate success/error responses and saved traces while actual PayPal calls retain authentication. Frontend checks verify masking of legacy create/capture token values, redaction after reload, and exclusion from activity logs and browser storage. The authorization method remains visible.
- Card Fields contract tests cover both pages, including no saved PayPal buyer, hosted-field eligibility/validation, lazy iframe rendering, SDK submission without a billing-address payload, SDK approval followed by backend capture, duplicate submissions/approvals, lost capture responses, status checks, reload/redirect recovery, and safe retries using the original key. The simulated authentication step remains interactive while other payment submissions are locked. Backend tests verify the card request's SCA preference, server-controlled amounts, ignored browser-supplied card data, buyer-cache preservation, and capture after the PayPal buyer changes.
- 3DS diagnostic regressions cover structured SDK errors, JSON embedded in error messages, iframe communication failures, safe identifier extraction without raw card/credential data, explicit cancellation followed by a rejected submit and late approval, and diagnostic logging of PayPal's authentication result without changing checkout state. Error categories are heuristic. These tests do not reproduce the reported live Sandbox iframe closing; the original generic activity entry did not contain the SDK failure reason.
- Recovery regressions cover both pages after cancellation, SDK errors, and rejected submissions: busy state releases, individual hosted fields close and rebuild, and another payment method can start without reloading. A pending old submit cannot capture or unlock a newer PayPal checkout after a late approval. An uncertain capture permits method selection and card editing while guarding payment submission; automatic read-only recovery and explicit capture reuse the original order within an active checkout. Approved raw card orders with no capture attempt can be abandoned for PayPal.
- Frontend callback logs and backend Get Order logs are tested separately. GET request/response traces include authentication results before capture and during status checks, stay redacted, and survive object restart. Failed authentication retains its GET result without sending capture. CardFields v5's public API was checked against PayPal's source/types: `onLookupComplete` is not exposed; no unsupported lookup callback is registered.
- Post-approval regressions reproduce a wrapped backend authentication rejection replacing the original error with the misleading uncertain-capture warning on both pages. The merchant callback now handles capture failures without throwing them through the SDK, retains original messages/debug IDs/3DS results, and automatically checks uncertain results without another capture. Tests cover automatic completed-transaction recovery, backend-confirmed unsent captures (including a failed follow-up lookup), uncertain dispatch guards, legacy capture responses without an attempted flag, late SDK errors during a pending capture or after recovery, and successful receipts despite a failed shared-method refresh. Backend status/error tests verify that the durable dispatch marker remains correct across preflight rejection, failed capture, and restart. These simulations do not identify the cause of the user's specific live payment failure; its original backend responses were not provided.
- Timing regressions verify that an early SDK submit resolution or rejection cannot unlock payment controls while the merchant's capture/recovery promise is still pending. Both cases wait for the original backend result and send only one capture.
- Fresh-checkout tests reload the new-customer page after actual simulated approved, pending, completed, and uncertain card attempts, plus a PayPal attempt. They verify no automatic order/operation lookup, a fresh unselected form and unchecked consent, enabled card checkout after render, new request UUIDs on submission, preserved returning-customer attempt keys, and an unchanged shared vault display. The last order ID remains separate and available only for diagnostics.
- Both pages' **Check last order status** tests verify one GET for an available ID, full response logging to Integration activity and browser console, and no checkout/receipt/control changes. Missing/invalid IDs make no request; a lost direct-charge response without an ID cannot trigger a retry. Error results only log details. A new attempt without a returned ID clears the older diagnostic ID. A slow diagnostic GET cannot block or overwrite a newer payment or its ID. Legacy request tokens in unrelated traces are excluded from diagnostic logs.
- Screenshot-driven recovery regressions cover restored voided orders, declined capture records, specific definitive decline responses, editable consent with a fresh order key, a resolved SDK submit without approval, and immediate recovery after a confirmed capture decline. Already-captured errors remain guarded. The SDK input style and iframe/container sizing were changed to avoid nested borders and overflow; no live visual result is claimed from the simulated DOM tests.
- Returning-load and provider-return recovery regressions reproduce the reported resource-not-found error: both pages continue loading the SDK/card fields, clear only an unavailable unpaid attempt, and create nothing until an explicit submission using a fresh key. Redirect recovery performs one lookup. Missing local orders and transient lookup failures are covered. Ordinary new-customer reloads skip this recovery path. Completed card/direct payments and successful capture traces restore without querying old PayPal orders. Possible captures keep their guard, including a durable capture marker saved before dispatch when no response trace exists. Backend tests verify the real 404 error shape/trace and marker persistence across restart. The simulated browser now awaits the entire startup promise instead of stopping at the first error message.
- New-customer selector checks cover no initial selection or rendered payment UI, one visible method at a time, lazy rendering after selection (including selection before the SDK loads), reuse across switching, preserved save choices, blocked hidden-method submissions, and locked selection during a card authentication challenge. Selection alone never sends a payment request.
- Wallet display checks on both pages cover Apple Pay on Safari on macOS/iPhone and Chrome on Mac/iPhone/iPad (including desktop-mode iPad), Google Pay on Android Chrome, and Apple Pay in browsers exposing ApplePaySession. The new page's selectable wallet radio reveals its disabled button. Each placeholder button has no payment handler.
- Save-consent tests cover unchecked/checked PayPal and card purchases, frozen consent during retries, unchecked consent on an ordinary new-customer reload, consent restoration on a payment-provider return, latest-method replacement across PayPal/cards, unchecked purchases preserving the prior method, and type-safe pending card vault webhooks. Card requests use SCA_ALWAYS. Server-side authentication checks reject absent, failed, incomplete, and attempted-only 3DS results before sending a capture.
- Saved-card tests cover a separate create/confirm sequence using the server-held vault ID, customer-initiated stored credentials, validated payer-action URLs, authentication redirects and read-only return recovery, explicit capture after successful authentication, lost confirmation retries, and stale cache revisions. The returning page keeps fresh PayPal/Card Fields and the wallet placeholder available beside the saved card.

Not verified in this session:

- Local Wrangler bundle validation: this execution environment rejected the npm registry request for Wrangler with HTTP 403.
- Visual/browser validation: Playwright was available, but Chromium was not installed. Downloading its browser runtime was blocked with HTTP 403, so the deployed PayPal iframe layout could not be visually verified here.
- Actual PayPal SDK rendering, Card Fields account eligibility, real 3DS challenges, and Sandbox transactions: runtime credentials remain in Cloudflare and no supported browser execution tool is available here. The deployed pages use the actual Sandbox SDK and REST API, not the test mocks.

Cloudflare builds and deployments are monitored through its GitHub check run; see the latest commit's check for the current deployment result. The README includes the runtime-variable and Cloudflare setup steps. No real secrets are included in this repository.
